## 1. 开发流程与协同规范

### 规则例外协议（Exception Protocol）
当所需分析工具或外部服务在重试一次后仍不可用，或满足某条硬性规则在技术上不可行且不增加安全/数据风险时，必须使用例外协议。例外必须经仓库维护者或项目负责人审批。在继续前，在任务跟踪系统或最终交付说明中记录受阻命令、证据、受影响文件、风险评估、补偿性检查以及最长 72 小时的有效期，并在 7 天内复核或移除。

### 任务跟踪与状态流转（Task Tracking）
任务队列是协同与防冲突的唯一事实来源。

- **流转状态**：
  `Backlog` (需求池) → `Open` (就绪可领) → `To Rework` (QA/审核未通过) → `In Progress` (开发中) → `In Review` (测试通过已推送，等待验收) → `Done` (已完成)。
- **防碰撞声明**：在编写任何代码前，**必须先将任务状态更新为 In Progress**，并附加启动评论（如：`🚀 开始处理此任务：[简要方案]`）。绝不认领或修改他人已处于 In Progress 的任务。
- **返工优先原则**：当存在 `To Rework` 状态的任务时，**必须优先于 Open 任务领取**。领取后优先阅读最新审查反馈并针对性修复。
- **任务阻塞协议**：若任务因环境、权限或外部依赖阻塞，将状态设为 `agent-blocked` 或退回 Open，并**必须评论三要素**：(1) 确切阻塞原因；(2) 诊断证据与错误日志；(3) 解除阻塞所需的操作或决策。

### 任务启动前准备
在修改任何代码之前：
- 完整阅读任务描述与所有上下文评论。
- **意图对齐与确认**：理解用户需求后，在任务最开始（或启动评论中）用简明语言复述一遍用户核心意图与交付预期，以防理解偏差。
- **按改动范围查阅与维护文档**：避免无差别通读全部文档造成上下文膨胀。根据任务改动范围阅读与更新对应文档：

| 改动范围 / 任务类型 | 建议查阅文档 | 文档维护与更新映射 |
| :--- | :--- | :--- |
| **跨模块调用 / 架构与依赖调整** | [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), [docs/adr/README.md](docs/adr/README.md) | 涉及新依赖、模块边界调整或核心模式变更时新建 ADR 并同步架构文档 |
| **核心实体 / 领域模型 / 公共抽象** | [docs/ABSTRACTIONS.md](docs/ABSTRACTIONS.md) | 抽象演进、数据模型变更时同步更新抽象定义与用法约束 |
| **UI 组件 / 交互模块** | 相关组件文档与设计规范 | 新增或变更高复用度组件时补充对应规范与示例 |
| **常规业务逻辑与缺陷修复** | 对应模块上下文及相关历史 ADR | 修复特定边界行为或业务假设变更时补充对应说明 |
- 对于涉及 UI 的任务，优先复用现有组件与设计规范，避免重复造轮子。

### 提交与推送约定
- 遵循常规提交信息前缀：`feat:`, `fix:`, `refactor:`, `test:`, `docs:`。
- 频繁提交（每 20-30 分钟或完成一个微小闭环）。
- 提交前与推送前必须通过质量门禁，**禁止使用 `--no-verify` 绕过门禁检查**。
- 任务只有在代码成功推送到远端主干/目标分支且通过验证后，方可标记为进入 In Review。

### 测试驱动开发（TDD 规范）
- 遵循 Red → Green → Refactor → Commit 循环。
- 缺陷修复必须编写重现该缺陷的回归测试用例，确认失败后再修复代码。
- **测试判断标准**：
  - 是否对应真实业务风险
  - 是否能在功能出错时失败
  - 是否会因无关重构而失败
  - 是否与其他测试重复
  - 是否更适合视觉回归或 E2E 测试
- **删除内容的测试原则**：
  - 用户指示删除的内容除非特意指明外，不添加已被删除的测试，仅单次验证已被删除即可。
- **测试执行效率**：
  - 从 Red 到 Green 的实现过程中不重复执行测试，避免无信息增量的重复执行浪费大量时间。
- 保持测试用例独立、行为导向、快速且确定性。

### 代码健康度与静态安全扫描
- **零新增告警规则**：新增的文件必须达到静态分析工具零告警标准。
- **童子军规则（Boy Scout Rule）**：修改已有文件后，该文件存在的告警数不得增加，必须保持或减少原有告警。
- 遵循健康度基线控制，确保代码重构与演进过程质量指标只升不降。

### 检查套件与验收门禁
在推送前，确保通过以下本地检查（按目标项目实际命令配置）：
```bash
# 代码风格与语法检查
[lint-command]
# 类型检查
[typecheck-command]
# 单元与集成测试（覆盖率达标）
[test-coverage-command]
# 全量构建
[build-command]
```

### 交付验收清单（Release Checklist）
在将任务流转至 In Review 时，在任务评论中提供完整的交付证据：
- 实现内容概要（涵盖核心业务逻辑与改动点）。
- QA 验证记录：执行的具体测试、命令或交互验证结果。
- 覆盖率结果：测试通过状态及覆盖率数据。
- 门禁检查结果：静态分析、构建与测试结果。
- 架构与文档更新：列出新增/更新的 ADR 或同步修改的架构文档。

### 架构决策记录（ADR）与文档维护
- 当涉及引入新依赖、变更存储模式、核心抽象演化或跨模块模式调整时，必须记录 ADR。
- 遵循历史 ADR 不可变原则：旧 ADR 生效后严禁修改正文，变更时新建 ADR 并标记替代关系。
- 产生核心抽象或架构变更时，必须在同一提交中更新相关架构与抽象文档。
